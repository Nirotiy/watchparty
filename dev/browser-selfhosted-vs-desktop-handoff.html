浏览器自托管端与桌面端差异

结论。网页端没有在桌面开发后整体停摆。Next.js 网页仍由当前自托管部署构建和运行，桌面基线之后还新增了网页媒体库标题墙、草稿审批和房间权限修复。已确认的主要功能缺口是：浏览器 MKV POC 仍隔离在 dev/browser-mkv-poc/，而正式网页播放器仍把 OpenList MKV 交给桌面端。仓库同时留着更早的根目录 Vite 客户端，不能把它与当前生产网页混称为同一前端。

能力对照

能力Next 网页端桌面端差异说明
房间创建、加入、受保护房间支持，网页本地保存访问 token 和最近房间支持，通过桌面会话与服务端桌面路由两套客户端入口和会话模型不同；房间快照与共享播放仍由同一 WatchParty 后端提供。
共享播放状态、播放列表和成员控制通过 Socket.IO 操作房间播放状态、队列、成员和权限经桌面适配器/本地宿主驱动原生播放器服务端状态共用，渲染/解码路径不同。桌面有本地播放器桥接和会话恢复，网页用 HTML 媒体播放器。
OpenList 媒体浏览与目录/标题管理文件列表、搜索、目录批量加入、标题墙、草稿审核与批准流程媒体库列表/搜索、目录导航、标题墙、草稿/排除管理并非桌面独占。两端视图实现不同，应逐端核对近期审批、撤回、权限错误和边界行为，不能只因桌面版本更新就假设网页缺失。
普通浏览器可播放视频依赖浏览器原生支持及 HLS/字幕适配由 libmpv/native playback 处理网页设备兼容性受浏览器解码器与跨源媒体头限制。
MKV正式播放器当前明确要求桌面端；OpenList 解析器也把 MKV 标为 browser unsupportedlibmpv 原生播放明确的产品缺口。POC 成果未进入 web/components/room-player.tsx，而且 POC 尚有基准机、WASM 回退、物理 A/V 与许可审查待办。
字幕外挂字幕列表、SRT 转 VTT、ASS 由 JASSUB 渲染；轨道和延迟是本地状态原生播放器字幕轨和外挂字幕网页 POC 已验证容器内 SubRip/ASS 的提取/渲染样本，但正式网页还没有接入这段流水线。
MPV / 桌面兜底可签发一次性交接码，页面不把交接凭证放 URL桌面端或 MPV 插件接收并继续同房间播放当前网页保留兜底，不是完整浏览器能力。
桌面设置与设备能力无原生设备、证书信任和 libmpv 设置页有连接配置、证书信任、后端 readiness、libmpv/native capability 和本地设置这些属于桌面运行环境，除非产品要支持浏览器连接多个服务，否则不是网页漏移植项。

当前自托管部署判断

  • Dockerfile.frontend 复制 web/、Next 构建产物及其依赖；也复制 desktop-shell/shared，因为网页构建共享其中部分纯逻辑。镜像不是桌面壳。
  • deploy/compose.vps.yml 以 Next npm start 在 loopback 13000 运行前端，后端在 18080；本地 Compose 默认映射到 3000 和 8080。
  • deploy/Caddyfile.vps 把 /api/*、/socket.io/*、/p/* 分别接到后端/OpenList，其他页面请求到 Next。浏览器 MPV 交接与目录批准 API 仍由此网页部署链提供。
  • VPS 配置与工作区有未提交变更。这里只核对了仓库文本，不表示已部署或生产环境已应用当前工作区版本。

MKV POC 已知状态

dev/browser-mkv-poc/RESULTS-libavjs.md 记载 libav.js + WebCodecs 路径、Chrome 非静音 5 分钟播放、Range 增量读取和本机回环测量结果。20 分钟测试曾通过，但测试机是 i7-14650HX、32GB、RTX 4060，高于原定 4 核、8GB、集显基准，不等同于基准机验收。

  • 未完成：基准机 1080p30 20 分钟；显示与 WASAPI 音频共同时间轴的物理 A/V 偏差测量；WASM 软件解码用户确认后的下载/运行路径；当前树 Edge 呈递异常；分发许可证和源码材料。
  • 已知范围：MPEG-2 已决定由媒体源转码；E-AC-3 和其他未覆盖编码目前保留 MPV 兜底。不要把 POC 的样本通过描述成任意 MKV 已覆盖。
  • 生产集成尚未做：签名 URL 生命周期、刷新、轨道偏好本地隔离、错误后的 MPV 兜底及房间播放状态衔接需在网页真实房间中实现和验证。

新 session 建议顺序

  1. 先固定目标：确认要恢复/维护的是根目录旧 Vite 客户端，还是当前 Next 自托管网页。默认从 web/ 开始，因为它是 Docker 与 VPS 实际部署的前端；将旧 Vite 另列迁移/下线问题。
  2. 以服务端路由和客户端调用做一次契约盘点：比较 web/lib/api.ts、web/lib/socket.ts 与 server/app.ts、server/core/http/、server/core/socket/；分别标出网页用到、仅桌面用到、未被任何客户端承接的服务端能力。
  3. 对照桌面提交序列，优先检查网页在 9 月 26 日后的媒体源契约、9 月底目录草稿批准、10 月初 owner/member 权限是否与桌面行为一致；现有提交证据显示网页已跟进这些主题，重点应是验收差异，不是预设遗漏。
  4. 单独审查旧 Vite 客户端的构建与服务端协议兼容性。根 README 的部署描述陈旧，CI 仍构建其 bundle，但 Docker 前端镜像只部署 Next。未完成端到端兼容检查前，不要删掉旧入口或把它作为受支持部署方式宣传。
  5. 再评估 MKV POC 产品化门槛。先补 POC 未完成的验证，再决定将 libav.js 流水线接入 web/components/room-player.tsx；保持房间共享播放状态不变，音轨/字幕偏好本地保存，失败时继续提供桌面/MPV 兜底。
  6. 每阶段输出：代码差异表、复现或测试命令、明确通过标准、是否需要改部署。未经明确指示不要触碰 VPS 或应用生产环境。
