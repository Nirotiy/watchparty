已确认的产品边界

目标是让浏览器承担 MKV 的增量读取、容器解析、解码和轨道呈现。第一阶段集中验证近 5 年的中端桌面电脑，移动端另行评估。

主题决定具体约束
服务端处理不运行 FFmpeg remux/transcode，不添加媒体代理。2 核、2GB、无独显的服务器不承担媒体处理或额外媒体流量。
媒体读取浏览器直连 OpenList 或媒体源。使用短时签名 URL。必须支持 CORS、HTTP Range 和浏览器可发送的鉴权方式。
URL 留存仅保存在内存中。到期前刷新。不写 localStorage，不进入房间同步状态或日志。
首发平台Windows、macOS 桌面 Chrome 和 Edge 当前稳定版。基准设备为近 5 年中端电脑、4 核 CPU、8GB RAM、集成显卡。
优先解码WebCodecs / 浏览器原生解码优先。按照具体媒体轨道检测解码能力。容器识别不能代替 codec 能力检测。
软件解码原生路径不支持时，先提示，再由观众确认加载多线程 WASM 解码器。仅打开 MKV 时按需加载，显示下载进度并使用浏览器缓存。仅纳入 LGPL 组件，排除 GPL 和 nonfree 编解码组件。
媒体数据必须 Range 增量读取，支持 seek。只读取 demux 和当前播放窗口需要的数据，避免完整下载媒体。
画质目标原生解码覆盖的常见编码以稳定 1080p30 为目标。4K / 高帧率尽力支持。WASM-only 编码记录能力和负载，不要求全部达到 1080p30。
字幕内嵌和外挂 SRT、VTT、ASS/SSA 可选轨。ASS/SSA 尽量保留样式。首发不支持 PGS 等图像字幕，需说明原因。
音频可切换内嵌音轨。输出到浏览器常规音频链路，如立体声或系统混音。特殊编码可由浏览器软件解码后输出 PCM。
多人同步房间时钟继续前进，不等待单个观众。轨道选择仅对当前观众生效。缓冲或解码落后由本地追帧，必要时提示性能不足。
失败兜底停止浏览器解码并说明原因，提供“交给 MPV”选项。媒体源无法满足浏览器访问要求，或持续无法达到可用播放质量时，保留 MPV 播放路径。

网页需评估并配置 COOP/COEP 跨源隔离响应头，以启用 SharedArrayBuffer 和 WASM threads。跨源字体、图片、脚本、媒体和其他资源要逐项核查 CORS/CORP，不能只验证播放器本身。

端到端播放流程

1. 获取临时地址签名 URL 只在内存中使用，并在过期前刷新。
2. 验证源能力检查 CORS、Range、鉴权和响应行为。
3. Range demux读取容器与轨道元数据，建立可 seek 的增量读取。
4. 选择解码路径先 WebCodecs / 原生。若不支持，征求同意后加载 WASM。
5. 播放或交给 MPV保留房间时钟；无法持续播放时给出明确兜底。
  1. 取得媒体源的短时签名地址。播放器在内存中保存地址和刷新所需状态，不把签名地址写入持久存储、房间状态或应用日志。
  2. 对源发起轻量请求，验证跨域策略、Range 请求和响应状态。确认浏览器能够用现有 URL 或标准授权机制访问。若必须依赖自定义 User-Agent 等浏览器不能设置的请求头，标记网页暂不可播。
  3. 以 Range 读取 Matroska 元数据和轨道信息。demuxer 按播放位置请求数据，seek 后读取新位置所需区间。网络层不可退化为先下载完整文件。
  4. 为每条视频、音频和字幕轨道建立能力结果。视频检查 WebCodecs 对具体 codec、profile、level、bit depth、分辨率等配置的支持；音频按实际 codec 和采样参数检查浏览器输出路径。不要仅以文件扩展名或 MIME 类型作结论。
  5. 选用观众本地支持的音轨和字幕轨。选择不写入房间同步状态。播放进度和同步时钟仍按房间现有机制共享。
  6. 若原生解码不能处理选中的轨道，说明将下载的软件解码组件及其状态，等待观众确认。确认后按需下载 WASM，显示进度，启动多线程软件解码。
  7. 解码后向浏览器视频和音频输出链路送帧或 PCM。持续观测解码耗时、缓冲、丢帧和音画同步。
  8. 网络或解码落后时，只让当前观众本地缓冲、跳帧或追赶。4K / 高帧率先降低实际显示帧率并保持音频与房间时钟。持续过载则停止并提示切换 MPV。

轨道和兼容策略

轨道 / 环节处理要求失败行为
容器解析从 Range 返回的数据中解析 Matroska EBML、Segment、Tracks、时间戳和 cue/index 信息。支持缺失或位于文件尾部的索引策略，并记录探测读取量。元数据无法解析、索引不可用且不能在约束内定位时，标记该文件暂不支持网页播放。
视频逐轨读取 codec ID 和必要参数。原生路径通过 WebCodecs / 浏览器能力探测及实际解码验证。稳定目标优先覆盖媒体库中占比最高的原生可解码组合。原生能力不匹配时提示 WASM。WASM 负载超出持续播放能力时停止并提供 MPV。
音频按需读取所选轨道，可切换内嵌音轨。保证输出浏览器可消费的 PCM 或其他常规输出格式，并正确处理时间戳、采样率和声道映射。轨道不受当前解码后端支持时，告知观众并列出可选音轨；没有可用轨道时提供 MPV。
文本字幕支持内嵌及外挂 SRT、VTT、ASS/SSA 作为本地可选轨。ASS/SSA 尽量保留定位、字体、颜色等样式。字幕时间相对于媒体时间轴渲染。解析或样式能力不足时显示基本文本或说明降级，不影响其他观众和房间时钟。
图像字幕PGS 等图像字幕不纳入首发必须支持范围。在轨道选择处标记暂不支持，建议选择可用文本轨或交给 MPV。
外挂文件外挂字幕也要满足浏览器跨域和访问要求。签名地址同样只在内存中保留，并处理过期刷新。外挂文件无法跨域读取时，该字幕不可用；不增加服务端代理。
媒体源访问检查 OPTIONS / 实际 Range 请求、允许来源、允许请求头、暴露的 Content-Range / Accept-Ranges / Content-Length 等响应字段和鉴权方式。不能提供浏览器所需的 CORS、Range，或要求浏览器无法设置的特殊请求头时，标记该源网页暂不可播，保留 MPV。

Range 验证要确认服务端返回的是请求的区间，并检查 seek 是否发出新的区间请求。只看到响应头中有 Accept-Ranges 不能单独视作验证通过。

实施阶段

阶段 0

只读盘点真实媒体分布

按媒体类型抽样现有媒体库。只使用 HTTP Range 读取容器头和轨道元数据，不完整下载，不修改媒体文件。记录 Matroska 版本和常见的视频、音频、字幕 codec、profile、bit depth、分辨率、帧率、声道及外挂字幕格式。

交付物是脱敏的编码分布表、样本来源能力表和候选测试样本清单。抽样规模及每类样本数量在实施时登记，避免把某个目录误当作全库分布。

阶段 1

隔离浏览器 POC

POC 与正式房间播放链路隔离。基于阶段 0 占比最高的真实组合验证 Range demux、轨道元数据、seek、WebCodecs 原生解码、观众确认后的 LGPL WASM 回退、字幕和音频轨切换、性能监控与 MPV 兜底。

桌面 Chrome / Edge 在 Windows、macOS 上分别跑样本。测试记录浏览器版本、操作系统、设备配置、媒体 codec 参数、网络条件和解码路径。

阶段 2

验证部署隔离和资源访问

在非生产测试环境启用 COOP/COEP，确认播放器页面可获得 SharedArrayBuffer 和 WASM threads。逐项检查身份认证、媒体源、字体、图片、脚本和其他跨源依赖，不以单个本地文件测试代替部署验证。

确认短时 URL 更新、内存清理、日志脱敏和浏览器缓存行为。验证跨域或 Range 不满足要求的源会明确转到 MPV 路径。

阶段 3

根据 POC 结果做产品集成决策

只有阶段 1 达到通过门槛，且阶段 2 的响应头与跨域依赖可部署，才进入产品集成。提交编码组合支持矩阵、已知限制、组件许可证和源码信息、WASM 下载大小及缓存策略、性能结果、失败原因列表和 MPV 兜底行为。

未通过的编码组合不默认为支持。可以缩小首发矩阵、替换组件或停止浏览器方案，再决定是否继续开发。

当前抽样结果与冻结的 POC 矩阵

2026-10-06 通过本机 OpenList 刷新分层样本，配额为 Anime 34、Film 1、TV Shows 15。50 个样本均可访问并成功通过 HTTP Range ffprobe；相较旧 manifest，替换了 8 个失效 Anime 路径。样本路径无重复。这是按作品分类的覆盖样本，不按全库视频总量加权。

轨道观察当前 50 个样本POC 覆盖

次级与高负载H.264 High 10 2 流、MPEG-2 720x480 3 流；另有 HEVC 2160p 样本。High 10、MPEG-2、4K HEVC 与多声道仅记录能力、WASM 负载和降帧行为，不作为首轮 1080p30 承诺门槛。

分层配额沿用现有 Anime / Film / TV Shows 方案，不能直接推导全库占比。codec 文件数可能因多音轨、多字幕轨而重叠；profile 表按探测到的轨道统计。外挂字幕只统计同目录且名称主干匹配的文件。

POC 首轮矩阵 v1（冻结）

  1. 原生验收基线：H.264 Main 8-bit、1920x1080、30 fps，AAC 立体声；按已确认门槛连续播放 20 分钟。H.264 High 8-bit 1080p / 23.976 fps 作为样本覆盖对照。
  2. 高频兼容路径：HEVC Main 10、1920x1080、23.976 fps，分别与 AAC 和 FLAC 立体声配对。先探测 WebCodecs；不支持时提示观众，确认后加载 WASM。WASM-only 结果单独记录，不纳入原生稳定承诺。
  3. 音轨与字幕：AAC / FLAC 立体声切换；外挂 ASS、SRT 与内嵌 ASS、SubRip 的本地选择和同步；PGS 识别后提示暂不支持。多声道音轨记录原生支持或 PCM 回退。
  4. Best effort：H.264 High 10、MPEG-2 SD、2160p HEVC Main 10、AC-3 / E-AC-3 5.1、FLAC 5.1 / 7.1。记录能力、WASM 资源负载和过载行为，不设全项通过要求。

矩阵优先级已冻结为：H.264 Main 1080p30 原生验收；H.264 High 8-bit 1080p 与 HEVC Main 10 1080p 做高覆盖对照；AAC / FLAC 立体声为主要音频；ASS / SRT 为可选字幕，PGS 仅提示不支持。任何轨道组合仍须在运行时单独探测，矩阵不构成设备兼容保证。

POC 通过门槛

基准目标适用于 WebCodecs / 浏览器原生解码覆盖的常见编码组合。WASM-only 组合单独记录负载和可播放时长，不要求每种达到稳定 1080p30。

项目通过标准记录方法
1080p30 连播基准设备上连续播放 20 分钟。记录每分钟解码帧、丢帧、缓冲、CPU / 内存和温度或降频迹象。丢帧率低于 1%。
音画同步播放过程中的音画偏差小于 100 ms。测量开始、运行中、seek 后及轨道切换后的偏差。
Range seek跳转后 3 秒内恢复播放。记录 seek 目标、Range 请求区间、请求耗时和首个恢复显示的视频帧时间。
增量读取整个测试过程不完整下载媒体。保存网络请求区间和累计读取量；确认播放窗口以外没有顺序下载到文件末尾。
原生能力判断WebCodecs 能力结果与实际样本解码结果一致。按 codec/profile/level/bit depth/尺寸等记录配置检查与真实解码错误，不仅记录 canPlayType 结果。
WASM 回退未经观众确认不下载、不启动；确认后可看到进度并能取消或失败退出。分开记录组件字节数、下载时间、缓存命中、线程数、CPU/内存、帧率和持续可播时间。
房间同步单个客户端缓冲或解码过载不暂停全房间时钟。验证本地追帧、跳帧与停止后 MPV 提示，不向其他观众同步个人音轨或字幕选择。

验收前固定基准媒体样本及哈希、测试设备和 Chrome / Edge 版本。测试结果须能区分网络、容器解析、解码器和字幕渲染问题。

风险与开放实现项

待验证项影响计划中的决策点
真实 MKV 编码比例决定首轮支持矩阵和优先样本。阶段 0 完成后，以抽样占比和可获得样本定 POC 主矩阵。
Matroska demuxer 选型影响 Range seek、索引处理、轨道元数据和 LGPL 义务。对候选实现检查许可证、源码提供方式、随机读取能力和浏览器集成情况；POC 前不锁定库。
WASM 解码器选型影响编码覆盖、包体、内存、CPU 负载和许可证边界。只纳入 LGPL 且无 GPL / nonfree codec 的配置。审查实际编译开关、依赖和分发义务。
SharedArrayBuffer 部署COOP/COEP 会改变跨源隔离要求，可能阻断未适配的依赖资源。在隔离测试环境逐项验证资源响应头和认证流程，再定部署方案。
签名 URL 刷新刷新时机或 Range 重试处理不当会中断播放；URL 也可能意外进入日志。验证过期前刷新、续播和错误脱敏，确认媒体提供方允许该访问模式。
ASS/SSA 样式浏览器文本轨不等同于完整 ASS 字幕渲染。对现有样本检查 libass 或其他 LGPL 方案的可行性、字体获取和样式差异，再写入支持矩阵。
性能门槛与设备差异WebCodecs 可用不代表指定设备能实时解码；WASM 性能更依赖浏览器和 CPU。分别报告 Windows / macOS 以及 Chrome / Edge 的结果。只对明确覆盖的原生编码路径承诺 1080p30。
缓存与组件体积首次启动等待时间可能较长，浏览器缓存策略和无痕模式行为不同。测量实际下载体积、冷启动和缓存命中，不把外部 CDN 可用性当作前提。

不在本阶段承诺“所有 MKV 任意编码必播”。最终可支持范围由真实媒体抽样、设备测试结果和可接受的客户端负载共同决定。

Jellyfin 的借鉴范围

Jellyfin Web 会生成客户端 DeviceProfile，列出容器、视频和音频 codec、码率及字幕交付能力。服务端 StreamBuilder 据这些能力选择 Direct Play、Direct Stream 或 Transcode。其文档说明，容器、音频或字幕不兼容时可能 Direct Stream，视频编码不兼容时可能转码，字幕烧录还会增加较重的服务端处理。

Jellyfin 做法本计划如何使用
客户端按浏览器和设备生成能力 profile。借鉴能力数据模型；本项目还需细化到每条轨道的 codec 参数和解码后端。
服务端统一评估容器、音视频和字幕组合。借鉴失败原因分类和兼容矩阵表达。解码选择放在浏览器，媒体源访问条件在播放前验证。
用 FFmpeg remux / transcode 弥补客户端差异。不采用。服务端资源预算和不增加媒体代理的产品边界不允许该回退。
通过服务器转换或烧录字幕。不采用服务端转换。浏览器处理文本字幕；PGS 首发提示暂不支持。

Jellyfin Web 的 MKV profile 仍把容器支持与音视频 codec profile 分开处理。因此不能把浏览器报告能播放 Matroska 当作任意 MKV 编码均可播。此处的设计要点是按轨道验证真实解码能力，并在 POC 中用真实文件确认。
